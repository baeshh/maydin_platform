# POS 장애 대응 · SQLite 백업 운영 방침

인터넷이나 서버가 끊겨도 약국은 판매를 멈추지 않는다. 대신 **장애 중 판매는 반드시 같은 거래 고유번호로 한 번만 서버에 들어가고, 장애가 끝나면 재고를 실제 수량으로 맞춘 뒤 장애를 닫는다.** 백업은 자동으로 만들고, 정기적으로 그 백업으로 서버를 실제로 띄워 복구 가능한지 확인한다.

## 1. 장애 감지

| 구분 | 어떻게 알아채나 | POS 표시 |
| --- | --- | --- |
| 인터넷 끊김 | 브라우저 `offline` 이벤트 | 빨간 칩 "인터넷 끊김 · 장애 중 판매" |
| 서버 연결 안 됨 | `/api/health` 요청 실패(5초 제한) | "서버 연결 안 됨 · 장애 중 판매" |
| 서버 오류 | `/api/health`가 503(DB 응답 없음) | "서버 오류 · 장애 중 판매" |

- POS는 평소 15초, 장애 중 5초마다 `/api/health`를 확인한다. 판매·검색 요청이 네트워크 오류로 실패해도 즉시 다시 확인한다.
- `/api/health`는 프로세스만이 아니라 DB에 `SELECT 1`까지 해 본다. 외부 모니터링(업타임 체크)도 이 주소를 쓴다.
- 장애 시작 시각은 POS 기기에 기록되고, 복구 후 서버의 **장애 기록**(`pos_outages`)으로 올라간다.

## 2. 판매 재시도와 거래 중복 방지

- POS는 결제할 때마다 **거래 고유번호**(`client_sale_id`, 무작위 UUID)를 만든다. 같은 장바구니·결제 내용으로 다시 보내면 같은 번호를 쓴다.
- 응답이 없거나 서버 오류(5xx)면 1초·2초 간격으로 최대 3번 자동 재전송한다. 화면에 "같은 거래 번호로 보내므로 두 번 저장되지 않습니다 · 카드를 다시 승인하지 마세요"가 뜬다.
- 서버는 `(약국, 거래 고유번호)`에 유일 인덱스를 두고, 내용 지문(sha256: 상품·수량·가격·할인·결제·회원·판매 시각)을 함께 저장한다.
  - 같은 번호 + 같은 내용 → 새로 만들지 않고 처음 저장한 영수증을 돌려준다(200, `duplicate: true`).
  - 같은 번호 + 다른 내용 → 409로 거절한다. 판매 내역을 확인해야 하는 상황이다.
- 3번 모두 실패하면 결제 화면 위에 선택 창이 뜬다: **다시 시도**(같은 번호) / **장애 중 판매로 보관** / 결제 화면으로.
  - VAN 데모 승인·포인트가 섞인 결제는 기기에 보관할 수 없다(서버 없이 승인·차감할 수 없음).

## 3. 장애 중 판매 (기기 임시 보관)

연결이 끊기면 POS는 자동으로 **장애 중 판매** 모드가 된다.

1. 상품 검색·바코드 스캔은 기기에 받아 둔 **장애 대비 상품 목록**으로 한다(10분마다·복구 직후 갱신, 바코드·판매가·구분만 보관, 고객 정보 없음).
2. 결제는 다음만 받는다.
   - 현금
   - 카드·간편결제·계좌이체: **카드 단말기 단독 승인** 후 단말기 영수증의 **승인번호**만 입력(카드번호·바코드는 입력·저장하지 않음)
   - 포인트·VAN 데모 승인은 쓸 수 없다.
3. 시스템 재고가 0이어도 실제로 건넨 상품은 기록한다. 모자란 수량은 복구 후 재고 대사에서 맞춘다.
4. 일반의약품·분류 전 상품은 평소처럼 약사 계정에서만 판매한다. 전문의약품은 POS에서 팔지 않는다.
5. "이 기기에 보관"을 누르면 **임시 영수증**(임시번호 = 거래 고유번호 앞 8자리)을 인쇄할 수 있다. 교환·반품은 복구 후 정식 거래번호가 생긴 뒤에 한다.
6. 보관 거래는 이 브라우저(localStorage)에만 있다. **장애 중에는 브라우저 데이터 삭제·시크릿 창·다른 PC 사용 금지.** 만일에 대비해 종이 장부에도 금액·결제수단·승인번호를 적어 둔다.
7. POS 화면을 새로 고쳐도 마지막 로그인 정보와 화면 파일(서비스 워커, https 또는 localhost에서만 동작)로 장애 중 판매를 이어 갈 수 있다. 이 기기에서 한 번도 로그인하지 않았다면 불가능하므로, 영업 시작 때 로그인해 둔다.

### 복구 후 자동 전송

- 연결이 돌아오면 POS가 장애 기록을 만들고(시작=장애 감지 시각, 종료=복구 시각) 보관 거래를 순서대로 같은 고유번호로 보낸다.
- 서버는 실제 판매 시각을 거래·결제 시각으로 기록하고, 출처(`OFFLINE_QUEUE`)·장애 번호·재고 부족분을 남긴다. 감사 기록 `POS_SALE_RECOVERED`.
- 비회원 복구 거래에는 가입 코드를 새로 발급하지 않는다(고객이 이미 매장을 떠났음).
- 저장에 실패한 거래(예: 직원 계정으로 일반의약품 거래)는 지우지 않고 **확인 필요**로 남는다. 약사 계정으로 다시 로그인해 "서버로 보내기"를 누르면 된다.
- 결제 직전 서버가 이미 저장하고 응답만 못 준 거래는, 처음 보낸 내용으로 다시 확인해 중복 없이 정리한다.
- 7일보다 오래된 거래는 복구할 수 없다(재고 실사로 맞춤).

## 4. 수기 거래 기록 복구 (약사 전용)

POS를 아예 쓸 수 없어 종이 장부에 적은 거래, 기기가 고장 나 보관 거래를 잃은 경우.

1. POS 하단 **장애 · 복구** → **수기 거래 복구 시작**.
2. 장애를 고르거나 새로 기록(종류: 인터넷·서버·정전/PC·기타, 시작·종료 시각, 메모).
3. 실제 판매 시각과 장부 메모를 입력하고 시작하면, 장바구니 위에 보라색 "수기 거래 복구 중" 띠가 뜬다.
4. 장부의 거래를 한 건씩 담고 결제를 입력한다(카드는 단말기 영수증 승인번호). 결제 화면에서 거래마다 판매 시각을 바꿀 수 있다.
5. 다 입력하면 **끝내기**.

- 거래마다 새 고유번호가 붙고 출처 `MANUAL`로 저장된다. 이미 전송된 거래를 다시 입력하지 않도록 **거래내역을 먼저 확인**한다.
- 직원 계정은 수기 복구를 할 수 없다(403).

## 5. 장애 후 재고 대사 (약사 전용)

장애 중 거래가 모두 서버에 들어간 뒤 진행한다. **다른 POS 기기에 보관 거래가 남아 있지 않은지 먼저 확인한다.**

1. **장애 · 복구** → 장애 목록에서 "대사 필요" 장애 → **재고 대사**.
2. 그 장애에 묶인 거래에 나온 상품마다 장애 중 판매 수량, 시스템 부족분, 현재 시스템 재고가 보인다.
3. 매대·창고에서 **직접 세어** 실제 수량을 모두 입력하고 **재고 대사 완료**.
4. 서버는 시스템 재고를 실제 수량으로 바꾸고(품절↔판매중 자동 전환) 재고 이력(`COUNT_ADJUST`, "장애 #N 후 재고 대사")과 감사 기록(`POS_OUTAGE_RECONCILE`)을 남긴 뒤 장애를 닫는다.
5. 닫힌 장애에는 새 복구 거래를 넣을 수 없다(409). 늦게 발견된 거래는 새 장애로 기록한다. 이미 저장된 거래의 재전송은 닫힌 뒤에도 중복으로 정상 처리된다.

재고 기준이 기존 POS(재고 파일 연동)인 약국은 수량을 기존 POS에서 실사·조정하고, MAYDIN에서는 **확인 완료만 기록**한다.

## 6. SQLite 자동 백업

- 서버가 켜져 있으면 6시간마다(`BACKUP_INTERVAL_HOURS`) SQLite 온라인 백업 API로 `server/backups/maydin-YYYYMMDD-HHMMSS-mmm.db`를 만든다. 쓰기 중에도 일관된 시점의 사본이 나온다.
- 만든 직후 그 파일을 읽기 전용으로 열어 `integrity_check`, `foreign_key_check`, 주요 테이블 건수, sha256 체크섬을 `manifest.json`에 기록한다. 검사에 실패한 백업은 `ok: false`로 표시되고 서버 로그에 남는다.
- 최근 30개(`BACKUP_KEEP`)만 남긴다. 마지막으로 복구 훈련에 성공한 백업은 개수를 넘어도 지우지 않는다.
- 백업 폴더는 `0700`, 파일은 `0600`(서버 계정만 읽기). 회원 이름·연락처가 들어 있으므로 **git에 올리지 않고**(`.gitignore`) 관리자 API로도 파일을 내려주지 않는다.
- **같은 디스크의 백업은 디스크 고장·랜섬웨어에 함께 잃는다.** 하루 한 번 `server/backups`를 다른 장소(암호화된 외장 디스크 또는 접근 제한된 클라우드 저장소)로 복사한다.

명령:

```bash
cd server
npm run backup            # 지금 백업 (서버가 켜져 있어도 됨)
npm run backup:status     # 최근 백업·복구 훈련 기록
npm run backup:verify     # 최신 백업 체크섬·무결성 검사 (파일 이름을 주면 그 파일)
```

본사 관리자는 `GET /api/admin/backups`(상태), `POST /api/admin/backups`(즉시 백업), `POST /api/admin/backups/drill`(복구 훈련)을 쓸 수 있다.

## 7. 복구 훈련 — 백업 파일이 있다고 복구가 보장되지는 않는다

서버는 7일마다(`BACKUP_DRILL_DAYS`) 최신 정상 백업으로 복구 훈련을 한다. 수동 실행: `npm run backup:drill`.

1. **체크섬·무결성 확인** — 백업 후 파일이 바뀌거나 깨지지 않았는지.
2. **임시 위치로 복원** — 운영 DB는 건드리지 않는다.
3. **복원본으로 서버 기동** — 실제 `src/index.js`를 빈 포트로 띄워 마이그레이션까지 마치고 `/api/health`가 DB 정상을 돌려줘야 한다.
4. **기동 후 데이터 대조** — 서버를 내린 뒤 다시 무결성 검사, 주요 테이블 건수가 백업 시점과 같아야 한다.

네 단계가 모두 통과해야 `manifest.json`에 성공으로 남는다. 실패하면 원인(예: "체크섬 불일치")이 기록되고 상태 화면의 마지막 훈련이 실패로 보인다. **마지막 성공 훈련이 7일보다 오래됐거나 실패로 남아 있으면 그날 원인을 확인한다.**

## 8. 실제 복구 절차

1. 서버를 멈춘다(복구 명령은 서버가 응답하면 거부한다).
2. `npm run backup:status`로 마지막 성공 훈련 백업을 고른다.
3. `npm run backup:restore -- maydin-YYYYMMDD-HHMMSS-mmm.db`
   - 백업을 다시 검사하고, 현재 DB를 `backups/pre-restore-*.db`로 남긴 뒤 교체한다(`-wal`/`-shm`/`-journal` 정리).
4. 서버를 켜고 `/api/health`, POS 최근 거래·재고를 확인한다.
5. **백업 시각 이후의 거래는 사라졌다.** 영수증·카드 단말기 매출 내역·종이 장부로 4번(수기 거래 복구)을 진행하고, 5번(재고 대사)으로 재고를 맞춘다.
6. 온라인 주문이 있었다면 결제사 관리자 화면과 대조한다.

## 9. 점검표

| 주기 | 할 일 |
| --- | --- |
| 매일 영업 시작 | POS 로그인(장애 때 화면 재시작 대비), 칩이 "온라인"인지 |
| 매일 마감 | "미전송 N건"이 없는지, 대사 필요 장애가 없는지 |
| 매일 | `server/backups`를 다른 장소로 복사 |
| 매주 | `npm run backup:status`에서 마지막 성공 훈련 날짜 확인 |
| 분기 | 다른 PC에서 8번 절차를 처음부터 끝까지 연습 |
