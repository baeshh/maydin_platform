# 데모·테스트 결제 운영 정책

## 원칙

**운영 DB에는 실제 돈이 오간 결제만 들어간다.**

데모·테스트 결제도 판매로 저장되면 실제 판매와 똑같이 처리된다. 다음 항목에 모두 반영되고, 지금 코드는 집계할 때 이를 따로 빼지 않는다.

- 매출 리포트, 대시보드, 영업 마감
- 재고 차감과 출고 내보내기(A형 "MAYDIN 판매 수량 내보내기")
- 포인트 적립

그래서 집계에서 빼는 방식이 아니라, **운영 DB에 들어오지 못하게 막는 방식**으로 지킨다.

| 결제 경로 | 개발 서버 | 스테이징 서버 | 운영 서버 |
| --- | --- | --- | --- |
| 데모 VAN 자동 승인(`VAN_DEMO`) | 허용 "(데모)" | 허용 | 카운터 방식 선택 불가, 승인 요청 409 `TEST_PAYMENTS_DISABLED` |
| 데모 Bridge(`demo: true` 결과) | 허용 "(데모)" | 허용 | 승인은 거절(`DECLINED`)로 기록, 실제 승인을 데모 취소로 환불하는 것도 409 |
| 데모 현금영수증 | 허용 | 허용 | 409 |
| 온라인 데모 결제사(`PG_PROVIDER=DEMO`) | 허용 | 허용 | 온라인 결제 닫힘 |
| 토스페이먼츠 테스트 키(`test_`) | 허용 "(테스트)" | 허용 | 온라인 결제 닫힘 |
| 토스페이먼츠 실결제 키(`live_`) | `PG_LIVE_ENABLED=true`일 때만 | 같음 | 같음 |
| 수동 승인번호 입력, 실제 단말기 Bridge | 허용 | 허용 | 허용(수동은 마감 때 영수증 대조) |

- 운영 서버: `NODE_ENV=production`
- 스테이징 서버: `NODE_ENV=production` 그리고 `MAYDIN_STAGING=true`. 운영과 **다른 DB**를 쓴다.
- 예전 변수 `ALLOW_TEST_PAYMENTS`와 `ALLOW_DEMO_PAYMENTS`는 더 이상 쓰지 않는다. 운영 서버에 설정해도 결제가 열리지 않는다.

## 운영 DB와 스테이징 DB를 섞지 않는다

운영 또는 스테이징 서버가 DB를 처음 열 때, 그 DB가 어느 쪽인지 `system_settings.data_environment`에 남긴다(`PRODUCTION` 또는 `STAGING`).

- **운영 DB를 `MAYDIN_STAGING=true`로 띄우면:** 서버와 `init-db`가 모두 시작하지 않는다. 운영 DB에 시험 결제를 열 수 없다.
- **스테이징 DB를 운영 설정으로 띄우면:** 서버와 `init-db`가 모두 시작하지 않는다. 시험 결제가 섞인 DB는 운영으로 옮길 수 없다. 운영은 새 DB로 시작한다.
- 개발·테스트 서버(`NODE_ENV`가 `production`이 아님)는 이 표시를 남기지 않는다. 개발 DB를 운영으로 옮기면 아래 경고와 초기 계정 차단에 걸린다.

## 이미 들어 있는 데모·테스트 결제 확인

```bash
cd server
npm run security:check                      # 운영 DB (DB_PATH)
npm run security:check -- --db /경로/백업.db  # 백업도
```

운영 서버를 시작할 때도 같은 내용이 `[보안]` 경고로 나온다. 다음 결제가 대상이다.

| 표시 | 뜻 |
| --- | --- |
| `MOCK` | 예전 온라인 주문의 가짜 결제. 결제사 연동 전 코드가 만들었다 |
| `DEMO/DEMO` | 데모 결제사로 받은 온라인 주문 |
| `TOSS/TEST` | 토스페이먼츠 테스트 키로 받은 온라인 주문 |
| `VAN_DEMO` | 데모 VAN 자동 승인으로 받은 POS 판매 |
| `VAN_BRIDGE`(데모 표시) | 데모 Bridge로 받은 POS 판매 |

금액이 음수인 줄은 그 판매의 환불이다.

## 확인된 경우 정리 절차

**금액·재고를 DB에서 직접 지우지 않는다.** 판매, 결제, 재고 이력, 감사 기록이 서로 묶여 있어 직접 지우면 대사가 깨진다.

1. 약국별, 기간별로 해당 주문 목록을 뽑는다. 주문번호, 금액, 상품, 처리한 직원을 확인한다.
2. 각 주문이 무엇이었는지 약국과 확인한다.
   - **시험으로 만든 판매(실제로 물건이 나가지 않음):** POS 거래내역 또는 파트너센터에서 취소·환불한다. 재고가 복원되고 매출은 음수 기록으로 상쇄된다. 데모 승인은 데모 취소로 되돌릴 수 있다. 운영 서버도 원래 승인이 데모일 때만 데모 취소를 받는다.
   - **물건은 실제로 나갔고 돈은 다른 방법으로 받음**(예: 별도 단말기, 현금): 판매는 그대로 둔다. 실제로 받은 결제수단·승인번호는 약국 장부에 적고 정산 담당자에게 알린다. 결제수단 기록을 DB에서 고치지 않는다.
   - **물건은 나갔는데 돈을 받지 못함:** 미수 처리를 정산 담당자와 결정한다. 시스템에서 판매를 지우지 않는다.
3. 정리한 뒤 `npm run security:check`로 남은 건을 다시 확인한다. 2번의 두 번째·세 번째 경우처럼 남겨 둔 건은 이 문서 아래 "남겨 둔 건" 표에 적어 둔다. 남은 건이 있으면 점검은 계속 종료 코드 1을 낸다.

## 시험은 어디서 하나

- 데모 VAN, 데모 Bridge, 테스트 키 결제창 왕복은 **스테이징 서버**에서 한다.
- 실물 단말기 현장 검증은 **실제 카드로 소액 승인 후 즉시 취소**하는 방식으로 한다. 이 거래는 실제 거래라 운영 DB에 남아도 된다. 판매 취소까지 해서 매출·재고가 원래대로 돌아오는지 확인한다. 절차는 [pos-field-verification.md](pos-field-verification.md)에 있다.
