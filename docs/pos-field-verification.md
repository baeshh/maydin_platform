# 실물 카드 단말기 현장 검증

실제 VAN 계약 단말기와 MAYDIN Bridge(또는 수동 승인)를 운영에 켜기 전에, 약국 카운터에서 아래 시나리오를 **실제 카드로** 해 본다. 모든 항목이 통과해야 그 약국·카운터의 카드 결제 방식을 바꾼다.

같은 상황을 서버 쪽에서는 `server/tests/phase18-van-crash.test.mjs`가 자동으로 확인한다. 이 테스트는 서버 프로세스를 실제로 강제 종료(SIGKILL)했다가 다시 띄우고, 데모 Bridge를 쓴다. 현장 검증에서는 이 자동 테스트가 대신할 수 없는 것을 확인한다.

- 실제 단말기와 VAN Agent가 같은 요청 번호에 같은 결과를 돌려주는지
- 단말기 영수증, VAN사 매출 내역, MAYDIN 기록이 서로 맞는지

## 아직 없는 것

- **NICE·KIS 서버 거래 조회 API:** `nice-adapter.js`·`kis-adapter.js`는 뼈대만 있어서, 조회를 부르면 "계약 후 연동" 오류가 난다. 지금은 Bridge(카운터 PC)의 조회 결과와 약국 관리자의 영수증 확인으로만 결과를 정한다. 연동하려면 다음이 필요하다.
  - 가맹점 번호
  - 카운터별 TID
  - 거래 조회 API 인증키
  - VAN Agent 연동 규격서
  - 테스트 가맹점
  - 운영 서버(`NICE_VAN_*`·`KIS_VAN_*`)의 `*_ENABLED=1`은 연동과 이 문서의 검증을 마친 뒤에 켠다.
- **실제 단말기용 Bridge 프로그램:** 저장소에는 데모 Bridge만 있다. 실제 Bridge는 VAN사 SDK로 [maydin-bridge-spec.md](maydin-bridge-spec.md) 규격대로 만든다. 현금영수증 발급·취소(§10)와 영수증 프린터 출력(§11)도 같은 프로그램이 맡는다.
- **현금영수증 VAN 전문:** 서버·Bridge 규격(용도, 식별번호 종류, 원승인번호·원거래일자·취소 사유 코드, 공급가액·부가세·면세 금액)은 국세청 현금영수증 항목에 맞췄지만, VAN사마다 전문 필드 이름·코드값이 다르다. 계약한 VAN사의 현금영수증 연동 규격서로 Bridge에서 바꿔 넣고 시나리오 8~10을 통과해야 한다.
- 그 전까지 실제 카드 결제는 **수동 승인**만 쓴다. 기존 단말기로 단독 승인한 뒤 승인번호를 입력하고, 마감 때 영수증과 대조한다.

## 준비

- 운영 서버(`NODE_ENV=production`, `MAYDIN_STAGING` 없음), 검증할 카운터 PC, 실제 단말기, 소액 결제용 법인카드 한 장
- 약국 관리자 계정(관리자만 할 수 있는 "승인 결과 직접 확인"이 필요)
- 검증용 상품 하나. 1,000원 안팎이고, 재고 수량을 미리 적어 둔다.
- 서버 로그를 볼 수 있는 사람 한 명. 서버를 멈추고 다시 띄워야 한다. 영업시간 밖에 한다.
- 기록할 것: 각 시나리오의 시각, 요청 번호(화면 또는 `van_transactions.request_id`), 승인번호, 단말기 영수증 사진, VAN사 매출 내역 캡처

## 시나리오

각 시나리오가 끝나면 **판매를 취소해 실제 승인도 취소**한다. 그래서 운영 매출·재고는 원래대로 돌아간다.

### 1. 정상 승인 → 판매 → 판매 취소

1. 상품 1개 → 카드 결제 → 단말기에서 카드 승인 → 판매 완료
2. 거래내역에서 취소 → 단말기 취소 → 환불 완료

통과 기준:

- 승인번호가 단말기 영수증, POS 거래내역, VAN사 매출 내역에서 모두 같다.
- 결제는 "단말기 확인"(`VERIFIED`)으로 기록된다.
- 취소 뒤 재고가 원래 수량으로 돌아온다. 리포트에서 판매와 환불이 상쇄된다.

### 2. 단말기 승인 직후 서버 중단

1. 카드 결제를 요청하고, 단말기에 카드를 꽂으라는 안내가 나오면 서버를 강제 종료한다. 테스트 서버에서는 `kill -9`, 운영 서버에서는 서비스 중지로 한다.
2. 단말기 승인이 끝난다(카드 청구됨). POS 화면은 "결과를 받지 못했습니다"를 띄운다.
3. 서버를 다시 띄운다.
4. POS에서 **카드를 다시 꽂지 않고** 「결과 조회」를 누른다.

통과 기준:

- 서버가 멈춘 동안이나 재시작 뒤에도 POS가 **새 승인을 요청하지 않는다.** 서버가 409 `APPROVAL_PENDING`으로 막는다.
- 결과를 확인하기 전에는 판매 취소와 영업 마감이 막힌다.
- 「결과 조회」 뒤 승인번호가 단말기 영수증과 같다.
- 판매 확정 뒤 재고가 1개만 줄었다. VAN사 매출 내역에 승인이 **1건**만 있다.
- POS 화면을 새로 열어도(브라우저를 닫았다 열어도) 상단 「승인 정리」에 그 승인이 보인다.

### 3. 판매 확정 중 서버 중단

1. 승인이 끝난 뒤 「결제 완료」를 누르는 순간 서버를 중단한다.
2. 서버를 다시 띄운 뒤 POS 화면이 띄우는 「다시 보내기」를 누른다. 같은 거래 고유번호로 보내진다.
3. 따로 한 번 더 해 본다. 판매가 저장되기 전에 화면을 닫으면, 그 승인이 「승인 정리」에 "판매에 안 씀"으로 남는다. 이때는 승인을 취소한다.

통과 기준:

- 판매가 **한 건**만 생긴다. 서버가 판매 고유번호로 중복을 막는다.
- 재고는 1개만 줄고, 승인은 한 판매에만 묶인다.

### 4. 승인 취소 후 재요청(고객이 카드를 바꿈)

1. 카드 A로 승인한다.
2. 결제 줄을 지우거나 결제 창을 닫아 승인을 취소한다. 단말기에서 취소가 끝나면 바로 서버를 중단한다.
3. 서버를 다시 띄운다. 「승인 정리」에 카드 A 승인이 "판매에 안 쓴 승인"으로 남아 있다.
4. 「승인 정리」에서 취소를 다시 진행한다. 화면이 같은 취소 요청 번호를 쓰므로 단말기는 같은 결과를 돌려준다.
5. 카드 B로 새로 승인해 판매를 끝낸다.

통과 기준:

- 3번 시점에는 새 승인이 막힌다(승인 합계 초과). 영업 마감도 막힌다.
- 4번 뒤 VAN사 매출 내역에 카드 A는 승인 1건, 취소 1건이다. 취소가 두 번 나가지 않는다.
- 판매에는 카드 B 승인만 쓰인다. 카드 A 승인으로는 판매가 확정되지 않는다.
- 단말기가 같은 취소 요청 번호에 **새 취소를 만들지 않고 처음 결과를 돌려주는지** 확인한다. 만들면 Bridge를 고쳐야 한다(규격 위반).

### 5. 판매 취소(환불) 중 서버 중단

1. 시나리오 4의 판매를 거래내역에서 취소한다. 단말기 취소가 끝나면 바로 서버를 중단한다.
2. 서버를 다시 띄우고 거래내역에서 같은 판매를 다시 취소한다.

통과 기준:

- 환불 주문이 1건, 재고 복원이 1번, VAN사 취소가 1건이다.
- 한 번 더 취소를 누르면 "이미 취소된 거래"로 거절된다.

### 6. 단말기 응답 없음 → 관리자 확인

1. 승인 중 단말기 전원이나 케이블을 뽑는다.
2. 「결과 조회」가 실패하면 약국 관리자가 단말기 영수증 또는 VAN사 매출 내역을 보고 결과를 정한다. 승인이 있으면 "승인됨(승인번호)", 없으면 "승인 없음"으로 정한다.

통과 기준:

- 직원 계정으로는 직접 확인이 거절된다.
- 관리자 확인 승인은 "영수증 대조 필요"(`UNVERIFIED`)로 남아, 마감 때 대조해야 한다.
- 감사 기록 `POS_VAN_RESOLVE`가 남는다.

### 7. 데모·테스트 결제 차단 확인(운영 서버)

1. 카운터 설정에서 "VAN 자동 승인 (데모)"가 선택 불가("운영 서버에서 사용 안 함")로 보인다.
2. 데모 Bridge(`npm run bridge:demo`)를 연결해 승인을 시도하면, 거절로 기록되고 판매에 쓸 수 없다.
3. 온라인 결제 설정(`/api/payments/config`)이 데모·테스트 키일 때 닫혀 있다.
4. `npm run security:check`에 데모·테스트 결제가 없다. 있으면 [payment-test-policy.md](payment-test-policy.md)대로 정리한다.

### 8. 현금영수증 발급 → 국세청 조회

1. 현금 판매에서 「현금영수증 → 소득공제 → 고객이 단말기 키패드로 입력」을 고르고 결제를 끝낸다. 고객(검증자)이 단말기 키패드에 본인 휴대폰번호를 누른다.
2. 같은 방식으로 「지출증빙 → 직원이 입력(사업자번호)」, 「자진발급」을 한 번씩 한다.
3. 1~2일 뒤 홈택스(검증자 본인 계정·사업자 계정)에서 발급 내역을 조회한다.

통과 기준:

- 단말기 영수증, POS 영수증, 홈택스의 승인번호·금액이 같다. 면세 상품이 섞인 판매는 공급가액·부가세·면세 금액이 홈택스와 같다.
- DB(`van_transactions.masked_identity`)와 서버 로그·Bridge 기록 어디에도 **가리지 않은 휴대폰·사업자 번호가 없다.**
- 자진발급은 `010-000-1234`로 발급된다.
- 13자리 숫자(주민등록번호 형태)를 입력하면 단말기·POS 모두 거절한다.

### 9. 현금영수증 응답 끊김 → 조회

1. 고객이 키패드에 번호를 누르는 동안 카운터 PC의 네트워크를 끊거나 Bridge를 종료한다.
2. POS가 "단말기 응답이 없습니다"를 띄우면 **다시 발급하지 않고** 상단 「승인 정리」에서 결과를 조회한다.

통과 기준:

- 결과를 확인하기 전에는 같은 판매에 새 발급이 막히고, 영업 마감도 막힌다.
- 조회 결과 발급돼 있으면 판매에 연결되고, 홈택스에는 **1건**만 있다. 발급 안 됐으면 새로 발급할 수 있다.

### 10. 부분 반품 → 현금영수증 취소 → 재발급

1. 시나리오 8의 판매(과세+면세 2개)에서 1개를 반품한다. POS가 단말기 현금영수증 취소를 먼저 진행한다.
2. 「남은 금액으로 다시 발급할까요?」에서 재발급한다.
3. 남은 상품도 반품(또는 판매 전체 취소)한다.

통과 기준:

- 취소 요청이 원승인번호·원거래일자·취소 사유 1(거래취소)·원금액으로 나간다. 홈택스에 원래 건이 취소로 바뀐다.
- 재발급 금액이 남은 상품 금액과 같다(과세·면세 구분 포함).
- 단말기 취소가 실패하면 반품이 저장되지 않는다.
- 반품 영수증에 "현금영수증 취소"와 원승인번호가 찍힌다.

### 11. 영수증 프린터 직접 출력

카운터 관리 → 영수증 프린터 → 「영수증 프린터 직접 출력 (Bridge)」로 바꾸고, Bridge의 `BRIDGE_PRINTER`를 실제 프린터(네트워크 `tcp://IP:9100` 또는 USB)로 맞춘다.

1. 「프린터 상태」 → 「시험 출력」. 한글·정렬·바코드·QR·자르기를 확인한다.
2. 현금 판매 → 자동 출력. 돈통이 열리는지 본다. 카드 판매는 돈통이 열리지 않아야 한다.
3. 용지를 빼고 판매 → 「영수증 출력 실패(용지 없음)」 → 용지를 넣고 「다시 출력」.
4. 덮개를 연 채로 출력 → 실패 안내 → 닫고 다시 출력.
5. 프린터 전원을 끈 채로 출력 → 「브라우저로 인쇄」로 대신 출력. 상단 「미출력 영수증」 칩이 사라지는지 본다.
6. 출력 중(종이가 나오는 동안) 카운터 PC의 네트워크를 끊었다 다시 연결하고 「다시 출력」.
7. 거래내역에서 같은 판매를 「영수증 출력」.

통과 기준:

- 2~6에서 영수증이 **한 장만** 나온다(같은 작업 번호는 Bridge가 한 번만 출력).
- 다시 출력·재출력에서는 돈통이 열리지 않는다. 7은 "[재출력] 시각"이 찍힌다.
- 한글이 깨지지 않는다(CP949). 58mm 프린터는 `BRIDGE_PRINTER_COLUMNS=32`로 줄이 넘치지 않는다.
- 용지가 거의 떨어졌을 때(근접 센서가 있는 기종) 출력은 되고 안내가 뜬다.
- USB 프린터는 운영체제마다 연결 방법이 다르다. Windows는 프린터 공유 이름 또는 USB 가상 COM으로 RAW 출력을 따로 확인한다(데모 Bridge는 `device:` 경로에 바로 쓰는 방식만 있다).
